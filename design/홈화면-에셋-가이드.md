## 1. 레이어 구조 — 잔디 게이지가 핵심

**전구는 통이미지 하나, 빛만 슬롯별로 켜집니다.**

```
┌─ grass-box.png   (928 × 619)   배경 + 꺼진 전구 4개(반투명 검정 워시)
│    ├─ bulb-glow.png × 완료 슬롯 (272 × 619)  ← **세로 전체 높이. x만 옮긴다**
│    ├─ bulbs.png (928 × 619)                 ← 전구 윤곽선. **(0,0)에 겹치기만**
│    ├─ 빨간 점 (코드로 그림)                   ← 현재 열린 슬롯 위
│    └─ 🔥 N일 연속 (폰트 텍스트)                ← 전구 **아래**, 잔디 박스 안쪽
```

### ★ 에셋이 캔버스를 맞춰 온다 — 코드는 겹치기만 (2026-08-11 재작업)

호랑이(`body` / `face` / `eye-shut`, 전부 1060 × 1111)가 문제없이 붙은 이유가 이것이고,
전구도 같은 방식으로 다시 만들었습니다.

| 파일 | 캔버스 | 코드가 하는 일 |
|---|---|---|
| `grass-box.png` | 928 × 619 | 그대로 깔기 |
| `bulbs.png` | **928 × 619** | **(0,0)에 겹치기만** |
| `bulb-glow.png` | **272 × 619** | **x만 이동**(세로는 전체 높이라 y 보정 불필요) |

`bulb-glow.png`의 빛 코어 중심이 **x = 135** 이므로, 슬롯 i의 좌표는 `전구중심 − 135` 하나뿐입니다.

> **재작업 전 상태(참고)**: `bulbs.png`가 654 × 211로 캔버스가 달랐고 전구 간격이 균등해
> 손그림 워시 전구와 정렬이 불가능했습니다. `bulb-glow.png`도 272 × 299라 y 보정이 필요했고,
> `%` + `aspectRatio` 조합이 어긋나 위치가 맞지 않았습니다.
> **캔버스를 맞춰 오는 쪽이 코드에서 좌표를 맞추는 것보다 언제나 낫습니다.**

**윤곽선(`bulbs.png`)은 빛 위에 얹습니다** — 그래야 켜진 전구도 테두리가 살아납니다.

### 실측 좌표 (`grass-box.png` 928 × 619 기준)

| 항목 | 값 |
|---|---|
| `bulbs.png` 윤곽선 중심 x | **205.5 / 377 / 544 / 717** (y 246–455) |
| `grass-box.png` 워시 전구 중심 x | 205.5 / 377 / 542 / 715 (y 252–448) — 윤곽선과 2px 내 일치 |
| `bulb-glow.png` 빛 코어 | x 70–200 (**중심 135**), y 257–439 / 빛무리 포함 y 200–460 |
| 빨간 점 | 중심 x = 전구 중심, y **205**(윤곽선 상단 246보다 위), 지름 26 |
| "🔥 N일 연속" | 전구 **아래**, y **472–552**, 글자 높이 81 |

**균등 4등분 공식(`(i+0.5)/4`)은 쓰지 않습니다** — 손그림이라 간격이 불균등합니다(171 / 167 / 173).
위 실측 중심값을 상수로 박습니다.

### ⚠️ 크기는 `%`가 아니라 `scale`로 직접 계산한다 (2026-08-13 실기기 사고)

게이지 이미지를 `StyleSheet.absoluteFill` + `height: '100%'`로 **부모 높이에 기대게 했더니
실기기에서 잔디와 전구가 3배로 커져 화면을 덮었습니다.** 같은 컴포넌트 안에서도
`scale`로 px를 직접 계산한 것(빨간 점·연속 텍스트)은 제자리였고, 부모 높이에 의존한
이미지만 넘쳤습니다. 호랑이가 멀쩡했던 건 `aspectRatio`로 스스로 높이를 정해
부모에 의존하지 않기 때문입니다.

→ 게이지는 전부 명시적 px(`928 * scale` × `619 * scale`)로 잡고 `overflow: 'hidden'`을 겁니다.
**근본 원인(왜 부모 높이가 안 잡혔는지)은 규명하지 못했습니다** — 같은 패턴을 쓰는
버튼·태양은 정상이었습니다. 비슷한 증상이 또 나오면 이 항목을 먼저 보세요.

코드: [components/home/GrassGauge.tsx](../components/home/GrassGauge.tsx)

### 빨간 점 (열린 세션 표시)

**코드로 그립니다** — 에셋 불필요. 현재 시각이 속한 시간대 슬롯의 전구 **위쪽**에 작은 빨간 원을 찍습니다. 데드존(새벽)에는 표시하지 않습니다.

## 2. 호랑이 + 말풍선은 한 장으로

시안에서 호랑이의 팔이 파란 타원을 감싸고 있어 **분리하면 이어붙이기가 더 어렵습니다.** 한 장(`tiger-hero.png`)으로 오려 주세요.

날짜·`DAY 47`·`단어 20개`는 **그 위에 폰트로 얹습니다** (이미지에 넣지 마세요 — 매일 바뀌는 값입니다). 파란 타원 안쪽 위치는 이미지를 보고 코드에서 맞춥니다.

### 탭 영역은 이미지 안에서 둘로 나눈다

이미지가 한 장이어도 터치는 나눌 수 있습니다. 이미지는 그리기만 하고, 그 위에 겹친 **투명 영역**들이 터치를 받습니다.

```
[tiger-body.png + tiger-face-*.png]   ← 그림 (터치 안 받음)
  ├ 투명 영역 A — 말풍선 자리          → 오늘의 단어장 진입 (탭)
  └ 투명 영역 B — 머리 자리            → 제스처 5종 (§2-8)
```

**제스처 5종은 투명 영역 B 안에서만 잡힙니다.** 말풍선은 별개의 탭 영역이라 서로 침범하지 않습니다.

#### 실측 좌표 (겹치지 않음 확인)

| 영역 | 히어로 좌표 (1060 × 1111) | 비율 left / top / width / height |
|---|---|---|
| **머리 제스처** | x 359–697, y 0–**350** | 33.9% / 0% / 31.9% / 31.5% |
| **말풍선 탭** | x 90–970, y **384**–954 | 8.5% / 34.6% / 83.0% / 51.4% |

머리 밑선이 y 281, 말풍선 위끝이 y 384이므로 **103px 여유**가 있습니다.
머리 영역을 **목까지(y 350)** 늘려 잡아도 34px이 남고, 그만큼 쓰다듬을 면적이 넓어져
아이 손가락에 편합니다.

위치는 **비율(%)** 로 잡아 기기 크기와 무관하게 따라가게 하고, 미세 조정은 실기기에서 합니다.

#### ★ 터치 영역은 머리를 따라 움직이지 않게 한다

이벤트 5에서 머리가 90px 튀어오르는데 터치 영역까지 따라 올라가면 추적이 꼬입니다.
**터치 영역은 애니메이션 컨테이너 밖에 고정**으로 둡니다. 문제가 없는 이유:

- 제스처는 **누르는 순간 캡처**되고, 그 뒤 머리가 어디로 가든 계속 추적됩니다
  (길게 누르는 동안 머리가 손가락 밑에서 빠져나가도 정상 작동)
- 이벤트 재생 중에는 어차피 새 제스처를 무시합니다

**제약**: 터치 영역은 **사각형만** 가능합니다. 머리는 둥글고 말풍선은 타원이라 실제 모양과 약간 어긋나며, 특히 **팔이 말풍선을 감싸는 부분**에서 오탭이 날 수 있습니다. 이미지를 조각내도 해결되지 않습니다 — RN은 투명 픽셀도 터치를 받기 때문입니다. 따라서 **팔·말풍선은 분리하지 않고 통이미지로 둡니다** (머리를 분리하는 이유는 터치가 아니라 애니메이션입니다 — 아래 참고).

### 애니메이션 — 머리는 분리한다 (2026-08-11 확정)

**말풍선·팔은 통이미지로 두고, 머리만 분리합니다.** 쓰다듬기(머리만 반응)와 하품(표정 변화)이
예정돼 있어 통이미지로는 불가능합니다.

| 연출 | 통이미지로 가능? |
|---|---|
| 숨쉬기(위아래), 통통 튀기기(scale), 전체 갸웃, 사운드 재생 | ✅ |
| **눈 깜박임 · 하품 · 표정 변화** | ❌ — 얼굴 분리 필요 |
| **쓰다듬을 때 머리만 반응** | ❌ — 얼굴 분리 필요 |

#### 구조 — 몸 1장 + 표정 N장

```
[히어로]  1060 × 1111
  ├ tiger-body.png             몸 (머리 없음, 목 위로 60px 연장)   ← 고정
  ├ tiger-claws.png            발톱 (평소 숨김, 이벤트 1에서만)
  └ [머리 컨테이너]             회전·이동 애니메이션 (회전축 532, 285)
        ├ tiger-face-●●●.png   기본은 normal, 이벤트 1에서만 yawn으로 교체
        └ tiger-eye-shut.png   깜박임 덮개 — 얼굴 **위** 레이어
```

#### 깜박임은 덮개, 표정은 통스왑 — 섞어 쓴다 (2026-08-11 확정)

**리스크가 비대칭이기 때문입니다.**

| | 빈도 | 변화량 | 윤곽이 1px 어긋나면 |
|---|---|---|---|
| **깜박임** | 3.5~6.5초마다, 앱을 켜놓은 내내 | 눈 점 2개 | 계속 떨려 보임 → **치명적** |
| **하품·표정** | 탭했을 때만 | 얼굴 전체 | 큰 변화에 묻힘 → 괜찮음 |

→ **고빈도·저변화(깜박임)는 덮개, 저빈도·고변화(표정)는 통스왑.**

이래서 `tiger-face-blink.png`는 만들지 않습니다 — 덮개가 그 역할을 합니다. 파일 수는 그대로입니다.
**이벤트 2(그르렁)도 `blink` 대신 덮개를 켜둔 채로** 처리하면 결과가 같습니다.

#### 회전축 — 실측값

목이 가장 잘록한 지점이 **y = 290 (x 468~596, 중심 x = 532)**, y 330부터 어깨로 벌어집니다.
머리 밑선은 y = 281.

```
회전축 = (532, 285)  =  가로 50.2% / 세로 25.7%   ← 턱 바로 밑
```

이 축이면 목은 가만히 있고 머리만 갸웃거립니다. **최대 ±5°**. 쓰다듬기 반응(살짝 눌리며 좌우로 흔들)도
같은 축을 씁니다.

RN은 뷰의 **중심**을 기준으로 회전하므로, 축을 옮기려면
`transform: [{translateX: px}, {translateY: py}, {rotate}, {translateX: -px}, {translateY: -py}]` 패턴을 씁니다.

**★ 표정은 반드시 `normal`을 복사해서 눈·입만 고칠 것.** 새로 그리면 얼굴 윤곽이 미묘하게 달라져,
갈아끼울 때 머리가 **떨리는 것처럼** 보입니다.

**하품 입이 턱 밑으로 내려와도 됩니다.** 캔버스가 히어로 전체라 잘리지 않고, 얼굴이 몸 위에 얹히니
벌어진 입이 목을 가리는 것도 정상입니다 — 캔버스를 크게 잡는 이유가 이것입니다.

**어떤 게 눈인지**: 얼굴 가운데의 **작고 동그란 검은 점 2개**.

### 2-2. `tiger-body.png` — 목 연장 60px + **상단 둥글게 마감**

머리를 그냥 지우면, 머리를 기울일 때 목 위쪽에 **투명한 삼각형 틈**이 생깁니다.

```
[그냥 지운 경우]            [목을 연장한 경우]
   ___                        ___
  /   \  ← 머리(기울임)      /   \
 ╱  ✗   ← 틈이 뚫림         ╱▒▒▒   ← 연장분이 틈을 메움
 │   │                      │▒▒▒│
 └───┘  목                  └───┘  목
```

머리 밑선이 **y = 281**이므로 연장분은 **y = 221까지(60px)** 올라갑니다.

**★ 목 윗부분을 잘린 단면이 아니라 둥글게 마감해서 그릴 것.** 평소에는 얼굴에 완전히 가려 안 보이지만,
**머리 분리 이벤트(4번)에서는 이 부분이 화면에 그대로 드러납니다.** 초안에서 "어차피 가려지니 대충"
이라고 한 부분이 이벤트가 정해지면서 **보이는 부분**으로 바뀌었습니다.

```
[평소]                [이벤트 4 — 머리 90px 상승]
  ___                      ___
 /   \  ← 얼굴            /   \    ← 머리
 │▒▒▒│  ← 목(가려짐)        ↕ 30px 갭  ← "분리"로 읽히는 부분
 └───┘                    ╭───╮   ← 드러난 목 60px (둥근 마감이 여기 보임)
                          │   │
```

연장 60px + 상승 90px = **30px 갭**이 남아 "분리"로 읽힙니다. 갭 없이 목만 늘어나 보이면 "분리"가 아니라
"목이 길어짐"이 되므로, 연장분을 60px보다 길게 그리지 마세요.

그 부분만 매끈해 보여 경계가 드러납니다.

```
1. 눈 바로 옆(볼 쪽)의 깨끗한 털 영역을 선택 → 복사
2. 눈 위에 붙여넣기        → 질감이 원본 그대로라 경계가 안 보임

4. 덮은 부분만 남기고 나머지 전부 지움 → 투명
5. 자르지 말고 PNG 저장
```

포토샵이면 **복제 도장(clone stamp)** 이 같은 일을 더 쉽게 합니다.

#### 왜 파내지 않고 덮나

"얼굴에서 눈을 지운 베이스 + 뜬 눈 / 감은 눈 2장"으로 가면 경계 문제가 원천적으로 없습니다.
대신 파일이 3개가 되고 얼굴에서 눈을 지우는 작업이 추가됩니다.
**위의 복사-붙여넣기로 경계가 해결되므로 덮개 1장으로 갑니다.**
실기기에서 경계가 거슬리면 그때 파내고, 그때도 이 덮개 파일은 `eye-shut`으로 그대로 씁니다.

### 2-7. 하품은 왜 2장인가 — 그림 교체는 시간이 안 흐른다

**한 장 스왑으로는 하품이 안 됩니다.** 하품은 *입이 점점 벌어지는 과정 자체*가 하품이라,
한 장을 갈아끼우면 입이 `[팍]` 열렸다 `[팍]` 닫혀서 **하품이 아니라 놀라서 소리지르는 것**으로 보입니다.
특히 **닫힐 때** — 벌어진 입이 갑자기 사라지는 게 제일 어색합니다.

#### 4개 이벤트 중 하품만 문제인 이유

| # | 이벤트 | 변화의 성질 | |
|---|---|---|---|
| 2 | 머리 내려감 | `translateY` — **연속** | ✅ 저절로 부드러움 |
| 3 | 갸우뚱 | `rotate` — **연속** | ✅ |
| 4 | 머리 분리 | `translateY` — **연속** | ✅ |
| 1 | **하품** | 그림 교체 — **불연속** | ❌ 중간 프레임 필요 |
| — | 깜박임 | 그림 교체 — 불연속 | ✅ 실제 눈도 순간적이라 이게 맞음 |

셋은 transform이라 저절로 연속이고 깜박임은 오히려 뚝 끊겨야 맞습니다.
**그림이 바뀌면서 시간이 걸려야 하는 건 하품 하나뿐입니다.**

#### 해결 — 입 크기 2단계 + 머리 모션

입 2단계면 충분합니다(3단계는 작업만 늘고 이득이 적음).
**`yawn2`(입 최대)를 먼저 그리고, 복사해서 입만 작게 고쳐 `yawn1`을 만드세요** — 얼굴 윤곽이
자동으로 같아져 떨림이 없습니다.

여기에 **머리가 뒤로 젖혀졌다 돌아오는 연속 모션**을 겹쳐 그림의 불연속을 덮습니다
(실제로 하품할 때 고개가 젖혀집니다).

```
0ms     normal          ┐ 머리 뒤로 젖히기 (rotate −6°, translateY −8px, 300ms)
120ms   yawn1  입 조금  │
280ms   yawn2  입 최대  ┘  + 발톱 팝인 + roar.m4a
        ─── 600ms 유지 ───
880ms   yawn1  입 줄어듦 ┐ 머리 복귀 (300ms)
1000ms  normal          ┘  + 발톱 사라짐
1180ms  깜박임 1회 (여운)
1400ms  끝
```

**닫힐 때 `yawn1`을 다시 거치는 것이 핵심입니다.** 여는 것보다 닫는 쪽이 어색해지기 쉽습니다.

#### 입이 원래 없는 게 유리하다

현재 얼굴은 주둥이에 **코 + 세로선**만 있고 입이 그려져 있지 않은데, 이게 우연히 잘 맞습니다.
그 세로선이 **입 다문 상태**로 읽혀서, 하품은 그 아래로 입이 벌어지는 것이 됩니다 —
만화적으로 자연스럽고 "없던 게 생기는" 위화감이 없습니다.

1개 발동인지 판정이 충돌하기 때문입니다. 갸우뚱 연출 자체는 사라지지 않고 탭 랜덤

### 2-8. 제스처 판정 — 쉬운 트리거로 같은 연출을 낸다

**연출은 그대로 두고, 트리거만 난이도가 낮은 것으로 고릅니다** (2026-08-11 확정, 2026-08-14
일부 재조정). 연출과 사운드가 재미를 만들지, 제스처의 정교함이 재미를 만드는 게 아닙니다.

> **2026-08-14 갱신 요지** — 탭 1회를 랜덤화하면서(§2-4) 탭 3연타를 폐기했고, 분리(이벤트
> 5)의 트리거를 **길게 누르기 → 아래로 당기기**로 다시 바꿨습니다. 아래 ①은 이제 당기기
> 기준으로 다시 쓰여 있습니다 — **2026-08-11에 당기기를 폐기했던 이유(아래 표)는 더 이상
> 유효하지 않습니다.** 왜 뒤집혔는지는 ① 앞의 설명을 보세요. 옛 판단을 그냥 지우지 않고
> 표에 남겨 둔 것은, 같은 문제(멈춤 판정·ScrollView 충돌)가 다른 제스처에서 재발했을 때
> "이미 검토했던 함정"으로 다시 참고할 수 있게 하기 위해서입니다.

#### 폐기한 안과 그 이유

| 폐기안 | 문제 | 상태 |
|---|---|---|
| 아래로 당겨서 **1초 유지** (시간 조건) | "아래로 간 뒤 멈춤" 판정에 속도 임계값 + 디바운스 필요 | 폐기 유지 — 당기기 자체는 부활했지만(아래 ①) 판정 기준은 **거리**(40px)로, 시간 조건은 여전히 안 씀 |
| 당기기 일반 (2026-08-11 당시) | ⚠️ 홈이 세로 스크롤이라 **ScrollView가 먼저 잡아채** 발동 자체가 안 됨 → `scrollEnabled` 토글 필요 | **뒤집힘 (2026-08-14)** — "머리 영역에서는 세로 스크롤이 막혀도 괜찮다"는 새 결정으로 이 문제 자체가 조건에서 빠졌다. `scrollEnabled` 토글 대신 `blocksExternalGesture`로 해결(아래 ①) |
| 길게 누르고 있기 (2026-08-11~08-13 채택안) | 트리거로서 "당기기"보다 부자연스럽다 — 머리를 누르는 동작과 "튕겨서 분리된다"는 결과가 손 감각으로 잘 안 이어짐 | **2026-08-14 폐기** — 당기기가 다시 가능해지면서(위 항목) 굳이 대체 트리거를 쓸 이유가 사라졌다 |
| 쓰다듬기 **횟수** 카운팅 | 누적 40px 스트로크 계산 + 손 뗀 뒤 300ms 판정 지연 필요 | 폐기 유지 (관련 없음) |
| 탭 3연타 (1.2s 판정창) | **탭 1회가 랜덤 이벤트가 되면서** "빠른 3번 탭"이 랜덤 3연발인지 3연타 1개인지 판정이 충돌한다 | **2026-08-14 폐기** — 갸우뚱 연출 자체는 탭 랜덤 풀에 남아 사라지지 않음(§2-4) |

#### ① 아래로 당겼다 놓기 (2026-08-14, 길게 누르기에서 재교체)

```
당기는 동안       머리가 손가락을 따라 내려감, 최대 −60px(디자인 px)에서 고무줄 저항
                  eased = MAX · (1 − e^(−dy/MAX))  (MAX = 60)
40px 도달         ▸ 장전(햅틱 툭 한 번, 이번 당기기당 1회만)
손을 떼면         armed(장전됨)면 ↑ 180ms  위로 90px 튕김 (Easing.out) + yelp.m4a
                              ─ 150ms  최고점 유지  ← 목 60px 노출 + 33px 갭 = "분리"
                              ↓ 300ms  스프링 복귀 (살짝 오버슈트)
                  armed 아니면(40px 못 채우고 놓음) 소리 없이 스프링으로 원위치
```

시간 조건은 없습니다 — "1초 유지"가 아니라 "40px 당기면 장전"이라 아이가 거리 하나로
바로 이해합니다(위 표의 "폐기 유지" 항목 참고).

`Gesture.Pan()`을 **아래 방향 전용**으로 잡습니다(`activeOffsetY([-100000, 12])`로 위쪽은
활성화 범위 밖에 둠) + 가로로 크게 움직이면 실패해 쓰다듬기(pet)에 양보합니다
(`failOffsetX([-14, 14])`). **`blocksExternalGesture(scrollRef)`로 ScrollView(세로
스크롤)를 이겨야** 실제로 당기기가 발동합니다 — 이게 2026-08-11에 당기기를 폐기했던
이유(위 표)를 무효화하는 핵심입니다: "머리 영역에서는 세로 스크롤을 포기해도 된다"는
새 결정 덕분에, ScrollView와 경쟁해서 이기는 것을 정공법으로 씁니다. 머리가 첫 화면의
전부가 아니라 일부 영역(§2 "실측 좌표")이라 다른 곳에서는 스크롤이 정상 동작합니다.

의미도 잘 맞습니다 — **당겼다 놓으면 튕긴다** = 고무줄/스프링. 아이 직관에 바로 붙습니다.

**"장전"됐다는 신호는 햅틱으로** 줍니다. 손가락이 머리를 가리고 있어 시각 신호가 안 보입니다.
`expo-haptics ~15.0.8`은 Expo Go 번들 포함.

목 연장 60px 규격(§2-2)은 그대로 유효합니다.

#### ② 쓰다듬기 "횟수" → **"시간"**

```
쓰다듬기 시작      → 그르렁 + 머리 내려감  (즉시)
1.5초 이상 계속    → 하품 + 손톱 + 어흥으로 전환
손 떼면            → 복귀
```

실제 고양이가 그렇습니다 — 골골거리다 계속 만지면 늘어져서 하품합니다.
**더 자연스럽고 더 쉽습니다.**

이 방식은 "즉각 반응 vs 횟수 판정 분리" 문제를 **문제 자체로 없앱니다.**
그르렁이 3번 울릴 일이 없습니다 — 계속 쓰다듬는 것이 곧 다음 단계이기 때문입니다.

쓰다듬기 Pan은 **좌우 전용**으로 잡습니다 → 세로 스크롤과 충돌 없음. 각도 기준은 아래 ④.

#### ③ 탭 지연 없애기

탭할 때마다 **이전 소리를 끊고 새로 재생**하면 판정 대기가 필요 없습니다 — 탭이 오면
곧바로(디바운스 없이) `isBusy`만 확인하고 랜덤 효과 하나를 바로 재생합니다.

이 앱에 이미 있는 TTS 패턴(`Speech.stop()` 후 `speak()`)과 같습니다.

> 2026-08-14 정정: 이전 버전은 이 절을 "3연타하면 소리가 끊기며 마지막 것만 들리고,
> 3번째에 갸우뚱이 발동한다"고 설명했지만, **탭 3연타 자체를 폐기**하면서(위 표) 이 설명은
> 더 이상 유효하지 않습니다. 지금은 매 탭이 `eventBusyRef`로 잠깐(0.2~1.2s) 잠기므로,
> 애초에 이전 효과가 끝나기 전에는 다음 탭이 씹히지 않고 무시됩니다 — "끊고 재생"이
> 필요한 상황(같은 효과가 겹쳐 재생되는 것) 자체가 잘 생기지 않습니다.

#### ④ 좌우 판정의 각도 — 36°

**세로 쓰다듬기는 넣지 않습니다.** 기술적으로 불가능한 게 아니라, 머리 위 세로 Pan이 스크롤을
이기게 만들면 **호랑이 위에서 화면 스크롤이 막히기** 때문입니다. 호랑이가 첫 화면의 큰 영역을
차지하므로 "이 화면은 스크롤이 안 되네"로 오해하게 되고, 시안이 화면보다 32% 길어(§7)
아래쪽 꽃·리본을 못 찾게 됩니다. **쓰다듬기 재미보다 스크롤이 중요합니다.**

실패 모드도 나쁘지 않습니다 — 세로로 쓰다듬으면 그냥 스크롤이 되고, 탭·당기기는 그대로 작동합니다.

> 이 절의 논리("머리 위 세로 Pan이 스크롤을 이기면 안 된다")는 **쓰다듬기(pet)**에만
> 적용됩니다. 당기기(①)는 정반대로 **의도적으로** 세로 방향에서 스크롤을 이기도록
> 만들었습니다 — 모순이 아니라, "머리 영역에서는 세로 스크롤을 포기해도 된다"는
> 2026-08-14 결정이 당기기에만 적용되고 쓰다듬기의 좌우 전용 원칙은 그대로이기
> 때문입니다. 즉 머리 위에서 위쪽으로 스와이프하면(스크롤 의도) 여전히 스크롤이 이기고,
> 아래로 당기면(분리 의도) 당기기가 이깁니다 — 방향으로 의도를 가른다고 보면 됩니다.

gesture-handler는 **각도로 판정하지 않고 축별 임계값 두 개를 경주**시킵니다. 먼저 닿는 쪽이 이깁니다.

**★ 코드에 각도를 쓰지 않습니다.** 아래 픽셀값 2개만 설정하고, 각도는 그 결과로 따라옵니다.
`if (angle < 36)` 같은 코드는 없습니다 — 아래 각도 환산은 **튜닝할 때 이 숫자를 만지면
어떻게 되는지 알기 위한 설명**입니다.

```js
Gesture.Pan()
  .activeOffsetX([-14, 14])   // X로 14px 가면 "쓰다듬기" 확정
  .failOffsetY([-10, 10])     // Y로 10px 가면 "쓰다듬기" 포기 → 스크롤
```

`Gesture.Pan()`은 **기본적으로 방향을 안 가립니다.** 아무것도 설정하지 않으면 머리 위의 모든
드래그를 잡아채 세로 스크롤이 죽으므로, 최소한 이 두 줄은 반드시 있어야 합니다.
`activeOffsetX` + `failOffsetY`는 "세로 스크롤 안에 가로 제스처 넣기"의 **표준 관용구**로,
커스텀 수학이 아니라 라이브러리가 제공하는 옵션입니다.

각도 환산 (`dx = d·cosθ`, `dy = d·sinθ`):

```
14·sinθ < 10·cosθ  →  tanθ < 10/14 = 0.714  →  θ < 35.5°
```

**수평에서 약 36° 이내면 쓰다듬기, 그보다 가파르면 스크롤.**

**왜 45°가 아니라 36°인가** — 두 오판의 대가가 다릅니다.

| 잘못 잡히면 | 결과 |
|---|---|
| 스크롤하려는데 쓰다듬기로 | 호랑이가 그르렁대고 화면은 안 움직임 → **짜증** |
| 쓰다듬으려는데 스크롤로 | 화면이 조금 움직임 → 다시 하면 됨 |

**스크롤 쪽에 유리하게 기울입니다.** 의도적인 좌우 쓰다듬기는 보통 수평 15~20° 안에 들어와서
36°면 여유가 충분합니다. 쓰다듬기가 잘 안 잡히면 `failOffsetY`를 12~14로 올립니다(41~45°로 넓어짐).

#### 최종 판정 기준

| 제스처 | 기준 |
|---|---|
| **탭** | 이동 10px 미만으로 눌렀다 뗌 (`maxDist`) |
| **쓰다듬기** | `activeOffsetX: ±14` + `failOffsetY: ±10` → 수평 ±36° |
| **당기기** | `activeOffsetY: [-100000, 12]`(아래쪽만) + `failOffsetX: ±14` + `blocksExternalGesture(scrollRef)` — 각도 개념 없음, 40px 이상이면 "장전" |

전부 실기기 튜닝 대상입니다.

#### 쓰다듬기 중 실시간 반응

손가락 쪽으로 최대 ±5° 기울기 + `scaleY` 0.97, 손 떼면 스프링 복귀. 회전축은 (532, 285).

> 폰트가 바뀌면 체감 크기가 달라집니다. 튜닝 지점: `HomeMenuButtons.tsx`의 `label.fontSize`,
> `TigerHero.tsx`의 `BUBBLE_LINES`, `GrassGauge.tsx`의 `STREAK_FONT_SIZE`.

## 7. 짚어야 할 문제 — 시안이 화면보다 깁니다

| | 비율 | 높이(1179 폭 기준) |
|---|---|---|
| 시안 | 1 : 2.83 | 3333 px |
| iPhone 15 Pro 화면 | 1 : 2.17 | 2556 px |
| 실제 콘텐츠 영역 (안전영역 제외) | | **약 2268 px** |

**시안이 약 1,065px(32%) 더 깁니다.** → **스크롤 허용으로 확정 (2026-08-10).**

시안 비율을 그대로 살리고 세로로 스크롤되게 합니다. 다만 **첫 화면(스크롤 전)에 무엇이 보이는지가 중요**하므로, 다음까지는 접히지 않게 배치합니다.

> 태양(설정) · 호랑이+말풍선 · 잔디 게이지 · 복습/발음체크/테스트 버튼

실기기에서 보고 조정할 부분이라 세로 여백은 고정값이 아니라 유동으로 잡습니다.

## 8. 구현 시 유의

### ★ 레이아웃은 `%`가 아니라 "시안 px × 배율"로 잡는다 (2026-08-11 확정)

에셋이 `호랑이잉글리시.png`(1179 폭)에서 **1:1로 잘렸습니다.** 확인:

| 에셋 | 에셋 폭 | 시안 실측 폭 |
|---|---|---|
| `btn-review.png` | 866 | 865 |
| `btn-test.png` | 875 | 874 |
| `deco-mountains.png` | 1179 | 1179 |

따라서 **각 요소의 폭 = 그 에셋의 픽셀 폭**이고, 배율 하나만 곱하면 시안이 그대로 재현됩니다.

```ts
const MOCKUP_WIDTH = 1179;
const { width: screenWidth } = useWindowDimensions();
const s = screenWidth / MOCKUP_WIDTH;   // 시안 px → 화면 px

// 폭도 간격도 전부 이 배율로
<Image style={{ width: 866 * s, aspectRatio: 866 / 247 }} />
```

**`%`를 손으로 잡지 마세요.** 부모에 `padding`이 있으면 `%`의 기준이 화면 폭이 아니라
축소된 폭이 되어 오차가 누적됩니다 — 실제로 이 버그가 났습니다(`paddingHorizontal: 20` +
어림잡은 비율 + 균일 `gap`이 겹쳐 버튼이 전부 어긋남).

### ★ 렌더 순서 — 잔디가 호랑이 발을 덮는다 (2026-08-14)

시안에서 **잔디가 호랑이 발 위에 그려져 있습니다**(겹침 구간 y 1369–1542, 173px).
따라서 코드에서도 **호랑이를 먼저, 잔디를 나중에** 그려야 합니다.
반대로 그리면 호랑이가 잔디 위에 떠 있는 것처럼 보입니다(실제로 그랬음).

- 잔디 이미지 위쪽은 풀잎 끝이라 거의 투명해서, **순서만 바꾸면** 발이 풀 사이로 비치는
  시안 모습이 그대로 재현됩니다 — 마스킹 불필요
- 잔디가 위로 올라가므로 `GrassGauge`에 **`pointerEvents="none"`이 필수**입니다.
  없으면 겹치는 말풍선 탭 영역 하단 16px의 터치를 잔디가 가로챕니다
- 버튼(y 2015~)은 잔디 끝(1988)과 **27px 여유**가 있어 영향 없습니다

### 시안 실측표 (`호랑이잉글리시.png` 1179 × 3333)

| 요소 | 폭(px) | 폭(%) | y 범위 |
|---|---|---|---|
| 태양 (설정) | 251 | 21.3% | 223–420 (좌측 여백 57) |
| 호랑이 | 1060 | 89.9% | 430–1560 |
| 잔디 게이지 | 928 | 78.7% | 1580–1981 |
| 복습 | 866 | 73.5% | 2016–2240 |
| 발음체크 | 867 | 73.5% | 2260–2509 |
| 테스트 | 875 | 74.2% | 2530–2773 |
| 꽃 (업적) | 135 | 11.5% | 2900–3089, 중심 x 28.6% |
| 리본 (획득물) | 176 | 14.9% | 〃, 중심 x 69.5% |
| 산맥 | 1179 | 100% | 3193–3332 |

**세로 간격은 균일하지 않습니다** — 태양→호랑이 10 / 호랑이→잔디 20 / 잔디→버튼 35 /
버튼끼리 20~21 / **테스트→꽃·리본 127** / 꽃·리본→산맥 104.
균일 `gap` 하나로 처리하면 안 됩니다.

**꽃과 리본은 크기가 다릅니다**(135 vs 176) — 하나로 통일하지 마세요.
좌우로 크게 벌어져 있어(중심 28.6% / 69.5%) 나란히 배치가 아니라 절대 배치입니다.

### 그 밖에

- **안전영역**: 상단 약 186px(다이나믹 아일랜드), 하단 102px(홈 인디케이터)은 비웁니다. 시안의 태양이 위쪽에 가까우니 확인이 필요합니다
- 줄노트 가로선은 화면 높이에 맞춰 개수를 계산해 그립니다
- 이미지는 `width` + `aspectRatio`로 크기를 줘 어떤 기기에서도 비율이 찌그러지지 않게 합니다
- **기존 기능은 그대로 두고 껍데기만 교체합니다** — 오늘 단어장 진입, 4슬롯 게이지 판정, 스트릭, 각 메뉴 라우팅의 로직(`lib/`)은 건드리지 않습니다
